# GOS v2.0.0 — K8s 发布策略引擎 三步走设计文档

---

## 总览

### 一句话定位

在 GOS 已有的"发布单 → Jenkins 构建 → GitOps 写回 → ArgoCD Sync"管道中，插入一层 **K8s 策略管理**，让平台可以声明式地管理 Deployment 的滚动更新策略、探针、资源限制、PDB，并通过 Git → ArgoCD 管道落地到 K8s 集群。

### 核心原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | **GOS 不直连 K8s** | 所有策略通过 Git → ArgoCD → kubectl apply 间接落地 |
| 2 | **ArgoCD 是唯一的 K8s 状态聚合代理** | 发布后状态跟踪走 ArgoCD API，不走 kube-apiserver |
| 3 | **策略快照嵌入发布单** | 快照存为 JSON 字段，与发布单同生同灭，不独立建表 |
| 4 | **渲染器输出通用 map** | `map[string]interface{}` 直接 deep merge 进 Helm values，兼容 Helm / Kustomize |
| 5 | **存量零改动兼容** | `strategy_snapshot_json` 为空时跳过策略渲染，行为完全不变 |
| 6 | **Argo Rollouts 预留不实现** | 枚举 / 字段 / 渲染器接口全部预留，v3.0 加一个 RolloutRenderer 即可 |

### 三步走总览

```
第一步：底座建模（1 周）
  │  建表 + 领域模型 + CRUD API
  │  交付物：4 张表、2 个 domain 包、2 个 SQL repo、2 个 Handler、完整 CRUD
  │
第二步：核心链路（1.5 周）
  │  策略解析 → 快照生成 → 预检 → 渲染 → GitOps 集成
  │  交付物：4 个 usecase、1 个 StrategyRenderer、修改发布单创建 + GitOps 执行
  │
第三步：回滚与闭环（0.5 周）
  │  状态回写 + 回滚恢复 + 前端展示
  │  交付物：app_release_state 扩展、回滚链路改造、详情接口增强
```

### 执行管道全链路

```
创建发布单                    执行 GitOps                     ArgoCD → K8s
    │                            │                              │
    ├─ 解析策略绑定               ├─ clone GitOps 仓库           ├─ render & apply
    ├─ 生成策略快照               ├─ 渲染 Values rules（现有）    ├─ Deployment Controller
    ├─ 策略预检                   ├─ ★ StrategyRenderer.RenderAll│   ├─ RollingUpdate 执行
    ├─ 持久化（含 snapshot）       ├─ ★ deep merge 进 values      │   ├─ Probe 检查
    │                            ├─ git add → commit → push    │   └─ PDB 约束驱逐
    └────────────────            └────────────────              └────────────────

发布后跟踪（Hook 机制）
    │
    ├─ 自动注入 argocd_health_check Hook（post_release 阶段）
    ├─ Hook 分派：POST ArgoCD Sync → 标记 running
    ├─ Hook 轮询：GET /api/v1/applications/{name}   ← 不连 K8s
    │    ├─ sync == "Synced" & health == "Healthy" → Hook success → 发布完成
    │    ├─ phase == "Failed" | health == "Degraded" → 按 FailurePolicy 处理
    │    └─ 其他 → Hook 保持 running，Tracker 下次继续轮询
    └────────────────
```

### 2.2 StrategyResolutionService — 策略解析

```go
type StrategyResolutionService struct {
    strategyRepo strategy.Repository
    k8sRepo      k8sinstance.Repository
}

func (s *StrategyResolutionService) Resolve(
    ctx context.Context,
    appID string,
    envCode string,
    releaseOverrides map[string]interface{},
) (*strategy.ResolvedConfig, error)
```

逻辑：
1. 查 `application_env_strategy_bindings`（appID + envCode）
2. 如果没有策略绑定 → 返回 nil（跳过策略渲染，存量兼容）
3. 查 `release_strategy_templates` 拿到模板的 `config_json`
4. 如果绑定有 `strategy_config_override_json` → 合并覆盖
5. 如果发布时有 `releaseOverrides` → 白名单内字段覆盖
6. 输出 `*ResolvedConfig`

```go
type StrategyPrecheckService struct {
    k8sRepo      k8sinstance.Repository

}

type PrecheckResult struct {
    Passed bool
    Checks []PrecheckItem
}

    Item    string // 检查项名称
    Status  string // "pass" / "warn" / "block"
    Message string
}

func (s *StrategyPrecheckService) Execute(
    ctx context.Context,
    appID string,
    envCode string,
    resolved *strategy.ResolvedConfig,

```

预检项设计：

| 检查项 | 阻断级别 | 说明 |
|--------|---------|------|
| 运行时绑定存在性 | **block** | `app+env` 未配置运行时绑定 |
| 交付引擎兼容性 | **block** | `strategy_engine=k8s_native` 但 `delivery_engine=jenkins` |
| K8s 实例策略支持 | **block** | `strategy_engine=argo_rollouts` 但实例不支持 |
| 探针端口合法性 | **warn** | 端口为 0 或格式非法 |
| 资源合法性 | **warn** | limit < request |
| PDB 合法性 | **warn** | maxUnavailable 可能导致全部不可用 |
| 副本数校验 | **warn** | replicas=0 |

### 2.5 StrategyRenderer — 策略渲染器 ★ 核心

```go
package strategy

type Renderer interface {
    // RenderAll 一次性渲染所有策略块
    RenderAll(snapshot strategy.Snapshot) (map[string]interface{}, error)

    // 以下为分块渲染，供调试
    RenderDeploymentStrategy(snapshot strategy.Snapshot) (map[string]interface{}, error)
    RenderProbes(snapshot strategy.Snapshot) (map[string]interface{}, error)
    RenderResources(snapshot strategy.Snapshot) (map[string]interface{}, error)
    RenderPDB(snapshot strategy.Snapshot) (map[string]interface{}, error)
}
```

**实现要点**：

1. `RenderAll()` 输入 `Snapshot`，输出 `map[string]interface{}`
2. 输出的 map 可以直接被 deep merge 进 Helm values.yaml
3. 对于 Helm values 约定为 `replicaCount` / `strategy` / `readinessProbe` 等命名
4. PDB 如果 `enabled=false`，不渲染 PDB 片段
5. 为 Argo Rollouts（v3.0 预留）保留了独立接口入口

**渲染示例**：

输入策略快照：
```json
{
  "strategy_type": "rolling_update",
  "resolved_config": {
    "replicas": 3,
    "rolling_update": { "max_surge": "25%", "max_unavailable": "25%" },
    "readiness_probe": {
      "enabled": true,
      "protocol": "http",
      "path": "/health",
      "port": 8080,
      "initial_delay_seconds": 10,
      "period_seconds": 5
    },
    "resource_requests": { "cpu": "500m", "memory": "512Mi" },
    "resource_limits": { "cpu": "2000m", "memory": "2Gi" },
    "pdb": { "enabled": true, "mode": "max_unavailable", "value": "1" }
  }
}
```

输出（deep merge 进 values.yaml 后）：


### 2.8 argocd_health_check Hook — 发布后健康轮询

**设计思路：** 不新建独立的后台轮询通道，而是复用 GOS 现存的发布模板 Hook 体系。新增一个 `argocd_health_check` Hook 类型，利用 Hook 框架已有的分派 → 轮询 → 结果判定链路。

#### 2.8.2 Hook 自动注入逻辑

在 `buildOrderSteps()` 中，当发布单 `delivery_engine = "argocd"` 时，自动追加 Hook 步骤：

```go

        return steps

        Status:    domain.StepStatusPending,
    }

```

#### 2.8.3 Hook 分派（dispatchArgocdHealthCheckHookStep）

```go
func (uc *ReleaseOrderManager) dispatchArgocdHealthCheckHookStep(
    ctx context.Context,
    order domain.ReleaseOrder,
    hook domain.ReleaseTemplateHook,
    step domain.ReleaseOrderStep,
) (bool, error) {
    // ① 从 order 中读取 argocd application name 和 argoCD 实例信息
    // ② POST ArgoCD Sync 接口触发同步
    argocdClient.SyncApplicationWithRevision(ctx, appName, revision, false)

    // ③ 标记步骤为 running，等待后续轮询
    uc.markStepRunning(ctx, order.ID, step.StepCode, "ArgoCD Sync 已触发，等待健康检查")
    return true, nil
}
```

#### 2.8.4 Hook 轮询（syncRunningArgocdHealthCheckHookStep）

```go
func (uc *ReleaseOrderManager) syncRunningArgocdHealthCheckHookStep(
    ctx context.Context,
    order domain.ReleaseOrder,
    hook domain.ReleaseTemplateHook,
    step domain.ReleaseOrderStep,
) (bool, bool, bool, error) {
    // ① GET ArgoCD /api/v1/applications/{name}
    app, err := argocdClient.GetApplication(ctx, appName)

    syncStatus := strings.ToLower(strings.TrimSpace(app.GetSyncStatus()))
    healthStatus := strings.ToLower(strings.TrimSpace(app.GetHealthStatus()))
    operationPhase := strings.ToLower(strings.TrimSpace(app.GetOperationPhase()))

    switch {
    case (syncStatus == "synced" || syncStatus == "") && healthStatus == "healthy" && operationPhase != "running":
        // 成功
        uc.markStepFinished(ctx, order.ID, step.StepCode, domain.StepStatusSuccess, "ArgoCD 健康检查通过")
        return true, true, false, nil  // updated=true, finished=true, failed=false

    case operationPhase == "failed" || healthStatus == "degraded":
        // 失败
        uc.markStepFinished(ctx, order.ID, step.StepCode, domain.StepStatusFailed,
            fmt.Sprintf("ArgoCD 健康检查失败：sync=%s, health=%s, phase=%s", syncStatus, healthStatus, operationPhase))
        return true, true, true, nil  // updated=true, finished=true, failed=true

    default:
        // 仍运行中，不更新状态
        return false, false, false, nil  // updated=false，继续等待下次轮询
    }
}
```

#### 2.8.5 与 Hook 框架的集成点

在 `syncHooksForStage` 中无需改动 — 已有的 `switch step.Status` 分发逻辑自动覆盖：

| Step 状态 | 框架行为 | 对应 argocd_health_check 动作 |
|-----------|---------|-------------------------------|
| `pending` | `dispatchTemplateHookStep()` | 触发 ArgoCD Sync → 标记 running |
| `running` | `syncRunningHookStep()` | 轮询 ArgoCD API → 判定成功/失败/继续等待 |
| `failed` | `FailurePolicy` 判定 | `block_release` 阻止发布 / `warn_only` 仅警告 |

#### 2.8.6 为什么复用 Hook 而非独立后台

| 维度 | 独立后台 goroutine | Hook 体系 |
|------|-------------------|-----------|
| 执行时机 | 全局轮询所有非终态单 | 精确到 post_release 阶段触发 |
| 失败处理 | 自行实现 | 复用 `FailurePolicy`（block_release / warn_only） |
| 环境过滤 | 自行实现 | 复用 `EnvCodes` 过滤 |
| 停用方式 | 改代码 | 模板中去掉 Hook 配置即可 |
| 扩展性 | 每次加功能需改 tracker | 新增 Hook 类型仅影响分派/轮询两个方法 |
| 代码量 | 独立 goroutine + 状态管理 | 两个方法（~60 行） |

## 附录 B：发布后状态跟踪方案 — 基于 Hook 机制

### 核心流程

```
创建发布单（delivery_engine = argocd）
  └─ buildOrderSteps()
       └─ injectArgoCDHealthCheckHook()
            └─ 追加 Step: "hook:post_release:argocd_health_check:900"

执行阶段（GitOps 写入 → ArgoCD Sync 触发后）
  └─ Tracker.Execute() → syncOrder() → finalizeOrder()
       └─ syncHooksAfterRelease()
            └─ syncHooksForStage(post_release, ...)
                 │
                 ├─ step.Status == pending
                 │    └─ dispatchTemplateHookStep()
                 │         └─ dispatchArgocdHealthCheckHookStep()
                 │              ├─ POST ArgoCD Sync
                 │              └─ markStepRunning("ArgoCD Sync 已触发，等待健康检查")
                 │
                 ├─ step.Status == running
                 │    └─ syncRunningHookStep()
                 │         └─ syncRunningArgocdHealthCheckHookStep()
                 │              ├─ GET /api/v1/applications/{name}
                 │              ├─ sync=Synced & health=Healthy & phase!=Running
                 │              │    → markStepFinished(success) → 发布成功
                 │              ├─ phase=Failed | health=Degraded
                 │              │    → markStepFinished(failed) → 按 FailurePolicy 处理
                 │              └─ 其他 → 不更新，下次 Tracker 周期继续轮询
                 │
                 └─ step.Status == failed
                      └─ FailurePolicy 判定
                           ├─ block_release → 阻止发布完成
                           └─ warn_only → 标记步骤成功但携带错误信息
```

### 为什么不直连 K8s（不变）

```
GOS ──(HTTP)──→ ArgoCD ──(watch/poll)──→ K8s Cluster
                    │
                    ├─ sync.status    ← Git vs K8s diff
                    ├─ health.status  ← Deployment/Pod 健康评估
                    └─ operationState ← Sync/Rollout 操作阶段
```

ArgoCD 作为 K8s 状态的聚合代理，三个字段已经足够 GOS 判定发布成功与否：

| 字段 | 语义 | 来源 |
|------|------|------|
| `sync.status` | Git 期望状态 vs K8s 实际状态是否一致 | ArgoCD diff 引擎 |
| `health.status` | K8s 资源是否健康（Deployment ready、Pod ready、探针通过） | ArgoCD health 评估引擎 |
| `operationState.phase` | 当前正在执行的操作（Sync/Rollout）是否还在进行 | ArgoCD 控制器 |

### 策略生效后的跟踪不变

加了策略渲染后，判定逻辑完全不变——只要 ArgoCD 报告 `Synced + Healthy`，就说明策略已经完整生效。因为策略已经嵌入 Deployment YAML 并写入 Git，ArgoCD 的 sync + health 本身就隐含了策略的一致性验证。

### 与现有 Hook 体系的对比

| Hook 类型 | 分派方式 | 是否有异步轮询 | 本轮新增？ |
|-----------|---------|:---:|:---:|
| `agent_task` | 派发 Agent 任务批次 | ✅ 是 | 已有 |
| `notification_hook` | 发送钉钉/企微通知 | ❌ 否 | 已有 |
| `webhook_notification` | HTTP POST 到配置 URL | ❌ 否 | 已有 |
| `argocd_health_check` | POST ArgoCD Sync → 轮询 API | ✅ 是 | **★ 新增** |

`argocd_health_check` 是第四个 Hook 类型，与 `agent_task` 一样采用异步分派 + 轮询模式，复用 Hook 框架的全部现有能力（阶段过滤、触发条件、失败策略、步骤状态机）。

# 应用接入向导

入口：应用管理 → 应用接入向导，或 `/system/quick-start`。首次安装后的业务配置、日常新增应用和已有应用补齐使用同一个入口，没有“全平台只运行一次”的限制。

## 安装前置条件

- GOS 已连接数据库、启动并可登录；管理员和内置标准字段沿用现有启动初始化。
- 执行端已有需要接入的 Jenkins 管线。安装配置中启用执行端、配置有效连接并同步管线列表；向导不生成管线、不改远端脚本、不测试执行。
- 具备相应管理权限。向导不会通过后台代替普通用户越权操作。

不要求预建项目、应用、自定义标准字段、应用绑定或发布模板，也不要求应用访问地址。语言和制品类型为可选分类。仓库、分支仅在明确选择对应参数来源时需要填写。

## 一次完整接入

| 步骤 | 用户操作 | 保存后得到什么 |
| --- | --- | --- |
| 基础检查 | 确认执行端启用、已同步的管线和环境；缺少安装配置时按提示处理 | 本次接入任务，不创建远端管线 |
| 项目与应用 | 选择已有项目或原地新建；填写应用名称、Key、负责人 | 项目引用和新应用 |
| 绑定管线 | 选择 CI、CD 或两者；读取所选管线的实时参数 | 当前应用独立的绑定，所选管线参数元数据 |
| 参数与标准字段 | 复用映射，或内联补建缺失字段；选择值来源 | 公共字段与缺失映射、当前应用的模板参数草稿 |
| 模板与流程 | 核对参数摘要，确认模板名称；按需显式修改应用审批流程 | 当前应用独立的发布模板，不改其他应用审批 |
| 完成检查 | 检查真实应用、绑定、模板、实时参数和审批配置 | 配置完成 / 待完善 / 暂时无法确认 |
| 开始使用 | 创建首个发布单，或继续新增应用 | 首单保持待执行；接入下一个应用不要求先执行首单 |

基础检查中的管线数量是已同步数据摘要，不等同于连通性通过。选择管线后实际读取远端参数，完成检查及创建首单前重新核对配置；读取失败不会当作零参数。

## 参数示例

假设 CI 有 `DEPLOY_ENV`、`PROJECT_NAME`，CD 有 `CI_JOB`、`CI_BUILD`：

- `DEPLOY_ENV`：没有映射时在当前页面新建 `deploy_env`，可以选择发布时填写。候选值以当前管线为准，不凭名称自动等同平台环境。
- `PROJECT_NAME`：可新建 `project_name` 并配置本应用固定值，也可每次发布时填写。不会自动假定它等于 GOS 项目名称。
- `CI_JOB`、`CI_BUILD`：使用对应内置运行时来源，不在配置时要求填写构建号；需要绑定 CI。依赖上游结果的 CD-only 会被阻止完成，独立输入的 CD-only 可以使用。
- 已有效映射的行默认折叠，可展开核对来源；固定值和自动来源不会变成首单表单中的重复输入项。

标准字段描述“参数是什么”，值来源描述“本次值从哪里来”。可选来源是发布时填写、固定值、发布基础信息、CD 沿用 CI 参数。固定值按布尔、数字和实际候选值验证。可选且非运行时参数可明确选择不传递，使用管线默认值。

共享映射已有非空值时在向导内只读；存在失效、类型冲突或歧义时明确处理，不静默重映射。仅对选中的管线同步参数，不停用其他管线的参数。敏感类型、动态候选、多选或不支持的插件参数转高级配置，不能将密码等存进普通草稿。

## 后续新增应用与已有应用

“新增应用（引导）”长期保留在菜单、应用列表和项目管理。完成页的“继续接入下一个应用”只预选当前项目，也可改选或新建项目。

可复用：项目、已有管线、公共标准字段及有效映射。

不复制：上一个应用的 ID、名称、Key、绑定 ID、模板 ID、固定值、构建号、审批设置、权限或首单记录。每个新应用拥有独立会话、绑定和模板。

已有应用从列表或详情选择“接入检查 / 继续配置”。可先按真实模板检查，无需先创建会话；一个异常模板不影响其他有效模板显示可用。继续配置时读取原配置并保护原资源：已有模板不覆盖、现有同阶段绑定不替换、审批默认保持、分类和高级应用信息不清空。只有一个模板时直接引用它；多个既有模板时，建议先检查并选择可用模板发布，或进入高级编辑器处理。

## 保存、冲突与失败恢复

- 停止编辑约 800ms 后保存非敏感草稿；刷新或重新登录后从接入中心恢复。实际项目、应用、字段和模板只在明确保存对应步骤时创建。
- 保存失败时保留当前输入并提示。离开未保存页面会提示，不把本地未保存内容当成服务端成功。
- 同一会话并发编辑采用版本校验。冲突后先重新载入服务器状态，不用旧版本强行覆盖。
- 步骤提交带幂等键，创建使用服务端确定的资源 ID；资源创建成功但响应丢失时重试恢复引用，不重复创建。
- 操作租约为两分钟，单次编排有超时和版本隔离；进程异常后稍后刷新重试。正常部分失败保存已完成资源引用并定位出错步骤。
- 放弃任务只停止该任务，保留已合法创建的项目、应用、字段、绑定、模板和发布单，不自动删除。
- 首单每个会话只关联一张；相同请求重试返回同一单，后续普通发布使用原创建入口。

`configured` 只表示配置检查通过。`verified` 需点击重新检查后确认所关联首单的实际成功状态；创建发布单不代表执行成功。执行仍由用户在原发布页明确触发，审批、权限、并发锁和执行预检照常生效。首单失败后的重试/重放沿用原功能，首版暂不将重放单重新绑定为向导验证单。

## API 契约

所有接口使用现有登录鉴权，成功响应为 `{ "data": ... }`。草稿/步骤请求中的 `expected_version` 来自最近响应；`request_key` 是调用者为一次逻辑提交生成的、最多 100 字符的唯一键。

| 方法与路径 | 请求 / 用途 |
| --- | --- |
| `GET /onboarding/status` | 执行端启用、已同步管线数、环境、我的最近 100 个任务 |
| `POST /onboarding/sessions` | `{mode, application_id?, project_id?}`；mode 为 `create_application` 或 `complete_application`，仅后者接受现有 application_id |
| `GET /onboarding/sessions/:id` | 读取可访问会话 |
| `PUT /onboarding/sessions/:id/draft` | `{expected_version, draft}`；完整替换当前草稿，不创建业务资源 |
| `POST /onboarding/sessions/:id/inspect` | 读取所选管线实时参数、字段建议、问题；不写业务配置 |
| `POST /onboarding/sessions/:id/steps/:step/apply` | `{expected_version, request_key}`；step 为 `preflight`、`identity`、`pipelines`、`parameters`、`template_flow`、`review` |
| `POST /onboarding/sessions/:id/check` | 重新检查配置和关联首单状态；不执行 |
| `POST /onboarding/sessions/:id/first-release` | `{expected_version, request_key, order}`；order 沿用标准创建发布单请求，应用和模板必须属于会话 |
| `POST /onboarding/sessions/:id/abandon` | `{expected_version}`；保留所有业务资源 |
| `GET /applications/:id/setup-status` | 按模板检查已有配置，不要求会话存在 |

会话字段包含 `id`、`owner_user_id`、`mode`、`status`、`current_step`、`version`、`draft`、`refs`、`check`、`first_release_order_id` 和时间。草稿 schema 及参数结构见生成的 `docs/swagger.yaml`。请求体上限 1MiB。问题字段为 `code/severity/step/field_path/message/remedy`，`check.status` 为 `ready/blocked/unknown`。

权限复用：应用管理、管线查看、管线管理、标准字段管理、执行器参数管理、发布模板管理；按实际步骤验证。首单额外校验目标应用和环境的 `release.create` 权限。会话仅创建者及具备管理权限的管理员可访问。403 是权限不足，409 是版本/幂等或资源冲突，422 表示配置暂不能完成；部分失败的响应可能附带最新会话，客户端应显示其资源引用与问题。

启动时新增迁移 `20260905_01_application_onboarding`，创建会话和幂等操作表，不修改已有业务记录。SQLite 使用 TEXT、MySQL 使用 LONGTEXT 存储类型化会话 JSON；所有者、版本和租约单独存储供查询与并发校验。
